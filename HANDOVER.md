# ShellSDR Handover

This document orients a new developer (human or AI agent) to the ShellSDR project so you can continue the work without re-deriving context. Read this first, then `SPECIFICATION.md` (the feature spec + step checklist) and `LESSONS.md` (durable decisions and pre-flight practices). Those three files are the source of truth; keep them updated as you work.

## 1. What ShellSDR is

A terminal (TUI) software-defined-radio receiver and recorder for Linux, optimized to run on a Raspberry Pi 3 (1 GB RAM). It talks to SDR hardware through SoapySDR (primary target: an SDRplay RSPduo), demodulates audio (NFM/WFM/AM/DSB/USB/LSB/CW), shows a power spectrum and waterfall, and (later) records to WAV with metadata and a scheduler. The UI is ratatui + crossterm, keyboard-first with a hard "no hidden shortcuts" rule (every action has a visible, focusable control).

It is built in strict TDD, in small vertical slices, each ending at a user-reviewed checkpoint. The user confirms each step on real hardware before the next begins.

## 3. How to build, test, run

From the ShellSDR directory. The toolchain is Rust edition 2024.

- Build (debug): `cargo build`
- Build (release): `cargo build --release`. ALWAYS use `--release` when running with real hardware; the debug build underruns the audio buffer and causes skipping that looks like a DSP bug.
- Unit tests: `cargo test`: currently 391 tests, all passing. Keep it green every slice.
- Lint: `cargo clippy --all-targets`: keep it warning-clean every slice. Use a narrowly-scoped `#[allow(dead_code)]` with a `NOTE(step->step)` comment for a symbol only consumed by a not-yet-wired future step, and remove it when that step lands.
- Format: `cargo fmt` before finishing a slice.
- Run against hardware: `cargo run --release` (opens the RSPduo via SoapySDR).
- Run without hardware: `cargo run -- --test` (deterministic `MockSource`, synthetic IQ).
- Alternate config file (per-instance, e.g. two RSPduo tuners): `cargo run --release -- --config tuner2` (→ `~/.config/ShellSDR/tuner2.toml` + `tuner2.schedule.v2.json`), or `--config-path /path/to/instance.toml` for an explicit file. Default config dir is `~/.config/ShellSDR/default.toml`.
- Examples (offline DSP harnesses):
  - `cargo run --example am_chain_dump`: pushes synthetic AM+noise through the real `VfoChain`, writes a WAV for FFT/PSD analysis. This is the harness that debugged the AM chain; reuse this pattern for any audio DSP A/B against SDR++.
  - `cargo run --release --example ssb_chain_dump [out.wav]`: USB speech-band tones + an opposite-sideband interferer + noise through the real `VfoChain`; prints per-tone levels, image rejection, passband ripple, peak and clip-free volume, and writes a WAV.
  - `cargo run --release --example iq_wav_demod -- IN.wav OUT.wav [offset_hz] [mode] [bandwidth_hz] [volume] [block]`: demodulates an SDR++ baseband (IQ) WAV through the real `VfoChain`, in SDR++-sized blocks (sample rate / 200) by default. THE gold-standard A/B: record a baseband in SDR++, play it back in SDR++ and record the audio, run the same file through this tool, then compare with `tools/analysis/bbcmp2.py` (phase-invariant alignment; two SSB demods with different LO start phase sound identical but have ~0 plain waveform correlation, so compare analytic signals). Match the bandwidth to what SDR++ used.
  - `cargo run --example audio_outputs`: lists the audio outputs the VFO Audio picker will show (cpal/ALSA PCMs + PipeWire sinks).

### Release packages for delivery (Docker)
`tools/dev build release arm64|x64|all` compiles `shellsdr` in a container built on the oldest supported system and writes `dist/shellsdr-<version>-<arch>.tar.gz` (`bin/shellsdr` + `share/shellsdr/themes/*.json`, installed with `sudo tar -C /usr/local -xzf ...`). `x64` builds natively on `ubuntu:24.04`; `arm64` cross-builds on `debian:trixie` with Debian's `aarch64-linux-gnu-gcc` and the arm64 multiarch `libsoapysdr-dev`/`libasound2-dev`. One parameterized Dockerfile, `docker/Dockerfile.build` (images `shellsdr-build:<arch>`, Rust pinned by `RUST_VERSION`). Compile only: the arm64 binary is not run (no qemu), so `cargo test` still runs on the host. Build output lives in `target/docker/<arch>/` and `target/docker/cargo-home/`, separate from the host `target/`. `debug` instead of `release` gives an unstripped `-debug` package; `tools/dev shell <arch>` opens a shell in the build container; `tools/dev image <arch>` rebuilds the image. The script prints the needed shared libraries and the newest glibc symbol version (currently 2.39 for both, which is the Ubuntu 24.04 floor). Target runtime packages: `libsoapysdr0.8`, `libasound2t64` and the device's SoapySDR module. User-facing install and build instructions are in `README.md`.

### Offline DSP analysis
When debugging audio DSP, analyze real/synthetic WAVs with FFT/PSD rather than guessing by ear. The analysis scripts are kept in the repo under `tools/analysis/` (`wavcmp2.py` level/band stats, `psdshape.py` normalized PSD shape, `fullcmp.py` full metric table incl. clip/crest/flatness/dynamics, `shiftvar.py` frequency-shift + within-file variance, `bbcmp2.py` identical-input phase-invariant A/B). They need numpy + scipy: `python3 -m venv /tmp/sdrvenv && /tmp/sdrvenv/bin/pip install numpy scipy`. Live A/B recordings made one after the other are confounded by HF propagation (two SDR++ takes of the same station differed by up to 10 dB in some metrics); only the baseband-file A/B (`iq_wav_demod`) isolates the DSP. Current result: with matched bandwidth, ShellSDR vs SDR++ on the same baseband has median phase-invariant similarity 0.999 and AGC level tracking within +/-0.3 dB.

## 4. Architecture overview

Three layers, kept separate so almost everything is unit-testable:

1. Pure state + reducers (no I/O): `app::AppState` holds all UI state; pure functions transform (state, input) -> state. Rendering is a pure function state -> ratatui frame. Only the thin event-loop edge (`ui::run`) touches the terminal.
2. The DSP engine (`engine::`): owns the source and a single processing graph on one DSP thread; communicates with the UI via a command channel (UI->DSP) and shared atomics / a drop-oldest slot (DSP->UI). cpal runs the audio callback on its own thread.
3. Hardware/IO behind traits (`source::SdrSource`, with `MockSource` for `--test` and tests; cpal audio; SoapySDR device) so logic is testable without hardware.

### DSP signal path (single graph, SDR++ model)
`SoapySource` (wideband IQ) -> DSP thread:
- Spectrum tap: wideband IQ -> `dsp::fft::SpectrumAnalyzer` (reshaper throttle -> Nuttall+/-1 window -> rustfft -> dB) -> drop-oldest slot -> UI (spectrum + waterfall). Skipped entirely in low-fi (both displays off).
- Per active VFO: `dsp::chain::VfoChain` mirrors SDR++'s RxVFO -> demod -> AF chain: NCO translate to the channel center (carrier, or carrier +/- bw/2 for USB/LSB per SDR++'s VFO reference) -> filtered channelizer (cascaded /2 FIR to the IF rate) -> channel LPF (bw/2) -> demod (FM quadrature with deviation bw/2; AM magnitude + DC block; SSB/CW frequency shift + `Re()`) -> AGC (AM/SSB/CW) -> post-demod LPF (AM bw/2, NFM bw/2, WFM 15 kHz) -> polyphase resampler to 48 kHz -> de-emphasis (WFM 50 us) -> clamp -> cpal. Every block was audited against SDR++ in Step 3.9; treat SDR++ as the source of truth for any DSP change.

### Threads
- UI thread (ratatui draw + input), DSP thread (`engine::dsp_loop`), cpal callback thread(s); with the Network source, a reader thread per connection (`shellsdr-remote`) instead of the DSP thread, and on the server a session thread with a reader. Runtime-adjustable params flow as `Command`s or atomics; structural changes (mode/bandwidth/center) rebuild the affected `VfoChain`. Neither UI nor DSP blocks the other.

## 6. Conventions and invariants (follow these)

- Strict TDD: name the seams to test, write the failing test, implement to green, one vertical slice at a time. Expected values come from an independent source of truth (SDR++, a worked example, a literal), never recomputed by the code under test.
- Keep `cargo test` green and `cargo clippy --all-targets` warning-clean every slice; run `cargo fmt`.
- "No hidden shortcuts": every action has a visible, focusable, labeled control; keyboard keys are accelerators for those controls. Verify this for any UI you add.
- Theme everything via semantic roles (`theme.rs`); never hardcode colors. The waterfall gradient (`waterfall` in theme JSON) colors both the spectrum trace (top stop) and the waterfall (full gradient).
- Persisted types use `#[serde(default)]` and are proven by round-trip unit tests; keep old configs loadable.
- Hardware/native code: SoapySDR/sdrplay prints to fds; keep the `log` no-op handler + the scoped `StdioSilencer` around device open/stream, and never `eprintln!` while on the alternate screen (use `log::warn!`).
- Terminal lifecycle (`ui::run::run`): after `EnterAlternateScreen` explicitly `Clear(All)` + `terminal.clear()` so the first frame repaints every cell; on exit (and in the panic hook) clear the screen *before* `LeaveAlternateScreen`. Terminals/multiplexers without a working alternate screen otherwise show the shell's text under the UI on start and leave the UI in the scrollback on exit.
- Writing style for the Markdown docs: one paragraph per line (no hard wraps inside a paragraph); use colons rather than en-dashes to join clauses. Lists/tables/code/headings are exempt.
- A save-triggered `cargo test`+`clippy` hook may exist under `.kiro/hooks/`; if present it runs on `.rs` save. Not required to build.

## 9. Key facts cheat-sheet

- Bookmarks: shared `~/.config/ShellSDR/bookmarks.v2.json` (not per `--config`; 0.1.x `bookmarks.json` is only read once to migrate); the per-instance TOML only holds the bookmark view (`[bookmarks]`: selected list, strip rows, sort). Text-capture mode: while a prompt/editor is open or the Find filter is being typed, printable keys are text (`AppState::text_capture` + `run::translate_text_key`), never accelerators. `--test` mode has no device in the device list, so Start does not stream there (pre-existing); check strip/spectrum alignment through the `strip_tick_sits_on_the_vfo_marker_column` render test.

- Hardware: SDRplay RSPduo, serial 22340A6E34, via SoapySDR 0.8.x + SoapySDRPlay 0.5.x. IFGR gain [20,59] dB, RFGR [0,9] dB; modes enumerate as separate devices via `mode=ST/DT/MA/MA8` and Slave. Dual-tuner = two processes, each with its own `--config`.
- Per-mode IF sample rates (SDR++ exact): NFM 50k, WFM 250k, AM 15k, SSB/DSB 24k, CW 3k. Default bandwidths and snaps are in `vfo::model`.
- Bandwidth editing is per-mode (`Mode::bandwidth_step` / `Mode::min_bandwidth`): CW steps by 100 Hz with a 100 Hz minimum (default 200, SDR++ range 50..500); all other modes step by 500 Hz with a 500 Hz minimum. Narrow CW bandwidths grow the channel FIR (taps = 3.8 * rate / (0.05 * bw)), so watch CPU on the Pi.
- Audio out 48 kHz mono, duplicated to all cpal channels; volume applied in the cpal callback from a shared atomic.
- FFT: size 4096, 20 fps, one-pole avg 0.5, dB = `10*log10(|X|^2/N^2)`, DC-centered via alternating-sign Nuttall window.
- Delivery: `tools/dev build release arm64|x64|all` -> `dist/shellsdr-<version>-<arch>.tar.gz`; x64 floor Ubuntu 24.04, arm64 floor Debian 13 Trixie (both glibc <= 2.39); no armhf. See section 3 and `README.md`.
- Config: TOML at `~/.config/ShellSDR/default.toml` (or `--config <name>` / `--config-path <path>`); themes JSON under `assets/themes` / `~/.config/ShellSDR/themes` / `$SHELLSDR_RESOURCE_DIR`, embedded fallback.
