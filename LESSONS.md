# Lessons learned

A running, reusable record of judgment from building ShellSDR. Two purposes: a progress log of decisions we made and why, and a pre-flight checklist of questions and practices to run through before and during any new software piece (especially a TUI). Add to the bottom as the project teaches us more.

## How to use this file

- Before starting a new feature or a new app, read the "Pre-flight questions" and the "Practices" sections and answer the relevant ones up front. Deciding late (e.g. retrofitting themes or resizability) costs far more than deciding early.
- When a decision or mistake teaches something durable, append it to "Decision log" with the date and a one-line rationale.

## Pre-flight questions for a new software piece

Run through these at design time. Each has bitten a real project when skipped.

### Presentation and UX
- Themed or not? If any color appears, assume themes will be wanted. Decide the theme model before writing the first colored widget, and reference semantic roles (text/dim/accent/border/selected/editing), never hardcoded colors. Retrofitting themes means touching every render call.
- External or built-in theming/assets? If themes/assets are external files, decide the search path and a guaranteed fallback up front (see Practices > Resources).
- Translated/localized or not? If yes, route all user-facing strings through a lookup from day one; retrofitting i18n is a large mechanical edit. If no, say so explicitly so contributors don't half-do it.
- Resizability and small sizes. What happens at the minimum terminal/window size? Decide clipping vs. scrolling vs. reflow before building panels. Content that can grow (lists of items, VFOs, log lines) needs a scroll/virtualization story early.
- Keyboard-first vs mouse-first. For a TUI: every action reachable by keyboard; mouse optional. Enforce a "no hidden shortcuts" rule: every shortcut maps to a visible, focusable control. Decide the navigation model (focus traversal, in-widget editing) once and apply it uniformly.
- Density and overflow. Long values (frequencies, paths, device names) overflow narrow columns. Decide wrap vs. truncate-with-ellipsis vs. scroll per field.
- Accessibility/legibility. Color contrast matters even in a terminal (our first retro green was too dark to read). Don't rely on color alone to convey state; pair it with text/shape.

### State, data, persistence
- Config format and location. Decide the format (we used TOML for config, JSON for themes) and the per-instance story (we support `--config <path>` so two RSPduo instances stay independent). Default to the OS config dir.
- Config versioning and forward/backward compatibility. Add a schema `version` and use `#[serde(default)]` so old/new files still load. Decide this before shipping the first persisted field.
- What persists vs. what's ephemeral. List it explicitly (we persist source, VFOs, bookmarks, UI toggles, theme; not transient edit buffers).
- Multi-instance / concurrency. Can two copies run at once? Over the same hardware/files? We mirror SDR++: last-closed-instance wins for shared config, and separate `--config` files isolate instances.

### Architecture and performance
- Target hardware budget. Name the floor (Raspberry Pi 3, 1 GB) and let it drive choices: bounded threads not thread-per-block, fixed modest refresh rates, early decimation, a low-fi mode that disables expensive work (FFT) entirely when off.
- Threading model. Decide the small fixed set of long-lived threads and the channels between them (UI thread + DSP thread + worker threads), and that neither UI nor DSP blocks the other. Prefer runtime-adjustable parameters via atomics over rebuilding graphs.
- Extensibility seams. Identify the plugin boundary before you need it (for us: decoders as VFO processors behind a trait). A seam defined early keeps later additions from reshaping the core.
- Dependency weight. Each dependency is a footprint and maintenance cost. Prefer a small, well-tested crate over a heavy framework when the heavy one's scheduler/buffers are unproven on the target (we chose a custom single DSP graph over FutureSDR, and the `soapysdr` crate after a spike proved it exposes what we need).
- Hardware/IO behind a trait. Wrap devices and external IO behind a trait with a deterministic mock, so logic is testable without hardware and a `--test` mode exists from the start.

### Process
- TDD seams agreed up front. Before writing tests, name the public seams to test and confirm them. Test behavior at those seams, not internals. Keep hardware/real-IO out of the unit suite; verify it manually.
- Throwaway spikes for unknowns. When an external capability is uncertain (does SoapySDR expose IFGR/RFGR separately?), write a tiny spike, learn, record the finding, delete the spike. Don't let unknowns drive the main design blind.
- Reviewable slices. Ship in small vertical slices, each buildable/testable/green, each ending at a user-reviewable checkpoint. Split large steps (we split "Master VFO" into UI-only Piece A and hardware Piece B) so untestable work doesn't block testable work.

## Practices worth applying by default (TUI + Rust)

These are tried patterns; apply unless there's a reason not to.

### TUI structure
- Separate pure state + reducers from rendering and from the IO/event loop. State transitions are pure functions of (state, input); rendering is a pure function of state to a frame; only the thin event-loop edge touches the terminal. This makes almost everything unit-testable.
- Render to a test backend. Use ratatui's `TestBackend` to assert on the drawn buffer (labels present, focused region framed, colors by role). Lets you lock UI behavior, including the visibility invariant, in tests.
- Translate raw input into an abstract action/intent enum at the edge; apply actions to state in a pure function. Keeps key-mapping testable and decoupled from crossterm specifics.
- Model focus and in-widget editing explicitly (a focus cursor + an editing flag + field cursor), with distinct visual states (idle/selected/editing). Don't overload one key to mean different things without a mode the user can see.
- Compute layout as pure geometry (area -> regions) so it's testable and so you can reason about minimum sizes and scrolling without a terminal.
- Degrade gracefully at tiny sizes and in non-TTY contexts (exit cleanly with an error, never panic).

### Rust specifics
- Keep the build and clippy warning-clean every slice. A warning now is a bug signal later. When a symbol is legitimately used only by a not-yet-wired consumer, add a narrowly-scoped `#[allow(dead_code)]` with a NOTE naming the step that will consume it, and remove it then. Don't let warnings accumulate.
- Embed critical assets with `include_str!` as a guaranteed fallback, while also shipping the same files externally for override. The app should never fail to start because a resource file is missing.
- Prefer `#[serde(default)]` and explicit schema versions on all persisted types.
- Derive `Default`/`PartialEq` where it keeps tests simple; avoid `Copy` on types that will grow owned data (we dropped `Copy` from app state once it held `Vec`/`String`).
- Expected test values must come from an independent source of truth (a spec, a worked example, a known-good literal), never recomputed by the same code the test checks.
- For resources, resolve a search path (env override > user config dir > dev/relative > system dirs > embedded) rather than a single hardcoded location. Document where each lives in dev vs. installed.

### Reference existing art
- When reimplementing a known tool (SDR++) or evolving a sibling (tuiner), mine it for the feature model, the data formats (we reused SDR++'s Zalias colormap and its filename-template idea), and the hard constraints (RSPduo single-tuner-per-process). But don't inherit its architecture wholesale if your constraints differ (GUI vs TUI, heavy DSP framework vs minimal).
- Verify assumptions about the referenced tool by reading its source, not by memory.

## Decision log

- 2026-10: Language/stack = Rust (edition 2024) + ratatui + crossterm; custom single DSP graph (not FutureSDR) for footprint control on Pi; `soapysdr` crate for devices after a spike confirmed IFGR/RFGR as separate gain elements on the RSPduo.
- 2026-10: Config = per-instance TOML (`--config`), default `~/.config/ShellSDR`; themes = external JSON with search-path loader + embedded fallback; both chosen before colored UI spread so nothing hardcodes colors.
- 2026-10: Interaction = keyboard-first with a hard "no hidden shortcuts" rule; uniform focus model (TAB between modules, Up/Down move field, ENTER to edit, in-field arrows, ENTER/Esc to commit/cancel); three visual field states (idle/selected/editing).
- 2026-10: RSPduo dual-tuner handled by two independent processes (single-tuner each), mirroring the user's SDR++ workflow; enumerate exactly what SoapySDR offers rather than special-casing master/slave.
- 2026-10: Lesson from review feedback: the first retro green (#005000) was too dark to read; lightened UI greens (#309030) while keeping authentic Zalias stops for the waterfall. Takeaway: legibility is a first-class theme constraint, and waterfall gradients are independent of UI text palette and must support arbitrary stop counts.
- 2026-10: Lesson from review feedback: fixed-size panels clip growable content; the left panel needs measured content heights + scrolling. Takeaway: decide the overflow/scroll story for any growable list before building its container.
- 2026-10: Scrollable panel built by rendering modules into an off-screen `Buffer` at full natural height, then blitting the visible slice, with a ratatui `Scrollbar` drawn only on overflow. Takeaways: (1) ratatui is immediate-mode, so scroll/scrollbar is computed from state each frame and resize needs no special event; (2) wrapping makes content height unpredictable, which breaks off-screen sizing, so the panel uses one-line-per-field (no wrap) and content is restacked to fit the fixed panel width rather than wrapping; (3) auto-scroll works at field granularity (focused field's virtual row span), not just module granularity, so a module taller than the viewport still scrolls the focused field into view; (4) reconcile scroll (clamp + ensure-visible) once per frame before draw, using the viewport height from the same layout function.
- 2026-10: First real persisted setting (last-used theme) went into the TOML `Config` with an `Option<String>` field and `#[serde(default)]`, plus `save` (creating parent dirs) and `load_or_default` (default on missing/malformed, warning on malformed). Restore on startup, persist on exit (best-effort, before handling the run result). Debugging note/trap: `cargo test` builds a separate test binary, so after editing `main.rs` the `./target/debug/<bin>` may be stale: run `cargo build` (or `cargo run`) before manually exercising the binary, or you'll test old behavior. The persistence logic itself is best proven by a pure round-trip unit test (select -> name -> config -> reselect), independent of the TUI.
- 2026-10: First hardware audio test exposed two DSP gaps that only real IQ reveals (synthetic unit tests used strong, clean signals so they passed). (1) The decimator dropped samples with no anti-alias filter, so for narrow modes (AM/SSB/CW) the whole captured band aliased into the channel and buried the signal; FM survived because it is wideband and strong. (2) AM/SSB/CW demods had unity gain on the tiny (~0.01-0.1) real IQ amplitudes, so output was inaudible, while FM's discriminator gain made it loud. Fix was to port SDR++'s actual reference implementation rather than invent: a Nuttall windowed-sinc channel low-pass (cutoff = bandwidth/2, transition = 10% of cutoff, N = 3.8·sr/transW) and its `loop::AGC` (peak-tracking, setPoint 1 / maxGain 1e7 / clip 10, per-mode attack/decay) applied to AM/DSB/USB/LSB/CW only. Takeaways: (a) when reimplementing a known tool, mine its exact parameters/formulas instead of guessing; (b) test DSP with weak and adjacent-interferer signals, not just strong clean tones, so these gaps surface in the suite; (c) a "silent" output is usually a gain/scale problem, a "noisy/buried" output is usually a filtering/aliasing problem.
- 2026-10: The AM "noise" turned out to be three compounding defects found only by proper FFT/PSD analysis of recorded WAVs (installed numpy/scipy in a venv for this): (1) running modes at the wrong IF rate, (2) substituting a cheap resampler (`rubato` FastFixedIn/Linear, ~-22 dB stopband) for SDR++'s polyphase FIR resampler (~-81 dB) so HF noise leaked into the audio, and (3) 13% hard clipping from level/DC issues. The fix was to STOP approximating and port SDR++'s actual `RationalResampler`/`PolyphaseResampler`/`PolyphaseBank` and its exact per-mode IF rates. Takeaways: (a) when a ported DSP tool sounds worse, suspect the piece you substituted rather than the piece you copied: the resampler quality (stopband depth) was the hidden culprit; (b) analyze real recordings with real FFT tools, comparing rms-normalized band energy and clip counts, not guesses; (c) a filter's stopband depth is set by the window (Nuttall is deep) but only if you actually run that filter: a linear interpolator has almost no stopband; (d) match the reference's sample rates exactly, because time constants (AGC attack/decay) and tap counts are all derived from them. Also: always build/run `--release` for real-time DSP; the debug build underran the audio buffer and caused skipping that looked like a separate bug.
- 2026-10: Final AM fix required three things, and the decisive technique was an OFFLINE harness, not hardware iteration: an `examples/am_chain_dump` that pushes a synthetic AM+noise+adjacent-carrier signal through the real `VfoChain`, writes a WAV, and is analyzed by the same FFT/PSD script used on the hardware recordings. This reproduced the clip/chirp deterministically and let each fix be measured. Root causes: (1) naive decimation aliased -> filtered channelizer (cascaded /2 FIR stages); (2) shallow resampler stopband -> ported polyphase resampler; (3) AGC set point 1.0 drove peaks past full scale -> lowered to 0.3 with a 0.9 ceiling for headroom. Key insight on the third: copying SDR++'s literal set point (1.0) was wrong for us because SDR++ relied on modest modulation + the sound card tolerating it; the robust engineering choice is explicit output headroom. "Port the reference" does not mean "copy every constant blindly": copy the structure/filters, but size levels for guaranteed no-clip. General technique worth reusing: build an offline signal->chain->WAV->FFT harness for any audio DSP so you can A/B against a reference tool objectively instead of guessing by ear. Also needed a binary+lib split (src/lib.rs) so examples/integration tests can import the crate.

- 2026-10: UI corruption on Start came from the SoapySDR/sdrplay native library printing `[INFO] devIdx: ...` to stdout/stderr while ratatui owned the alternate screen. Layered fix: enable the `soapysdr` crate `log` feature + call `configure_logging()` so `SoapySDR_logf` output is routed to the `log` crate and discarded (no logger installed), set `SOAPY_SDR_LOG_LEVEL=0`, and wrap the device-open/stream-activate calls in a scoped `StdioSilencer` that `dup2`s fds 1 and 2 to `/dev/null` and restores them on drop (for any line that bypasses the handler). Plus a `terminal.clear()` after a successful Start to repair residual corruption, and never `eprintln!` while on the alt screen (route to `log::warn!`). Takeaways: (a) native C libraries behind a Rust crate can still write to the process's fds; a log handler alone is not always enough, so keep an fd-redirect guard as the belt-and-suspenders layer; (b) confirm the print path with `strings libXxx.so` before assuming how a lib logs.
- 2026-10: Device/audio selection modeled on SDR++'s three separated phases: enumerate (cheap, no handle) -> select (open briefly, probe ALL capability lists, close) -> start (open and hold). `SourceModule::select_device` takes a probe closure so the pure model is testable with the mock while the binary uses real SoapySDR. Per-device settings persist in a `source_devices` map keyed by the device args string, stored by value/name (sample rate value, antenna name, gains by element name) not list index, so they survive driver capability reordering; other devices' entries are preserved across saves. Takeaway: keep enumeration/selection/start distinct, re-resolve a saved selection against fresh enumeration (fall back to first device if gone), and key persisted sub-settings by name so a driver update doesn't scramble them.
- 2026-10: cpal's ALSA backend does not expose individual PipeWire sinks (only the generic `pipewire` PCM and raw `hw:`/`plughw:` devices), so a user's `VirtualSink` was invisible. Fix without adding a JACK/PipeWire dependency: enumerate PipeWire sinks via `pactl list sinks` (parsed as `Name:`/`Description:` pairs), and to play to one, open the generic `pipewire` cpal device with the `PIPEWIRE_NODE` env var set to the sink's node name, scoped around the stream open by a guard that restores the previous value. An `AudioTarget` enum (Default / CpalDevice(name) / PipeWireSink(node)) round-trips through a single canonical string (`pw:` prefix for sinks) so it persists in the existing `Option<String>` field, backward-compatible. Verified the routing with `speaker-test -D pipewire` + `PIPEWIRE_NODE=VirtualSink` + `pw-link -l` before wiring it. Takeaway: when an abstraction layer hides targets, find the layer that does expose them (PipeWire via pactl) and the documented env/PCM hook to bind to them, and verify at the shell before coding.
- 2026-10: Power spectrum + waterfall ported SDR++'s exact FFT recipe rather than invented: reshaper throttle (`interval=round(sr/fps)`, `keep=min(interval,N)`, `skip=interval-keep`) decouples frame rate from sample rate; a Nuttall window multiplied by an alternating +/-1 sign does the N/2 fftshift in the time domain so the FFT output is DC-centered with no post-swap; dB = `10*log10(|X|^2/N^2)`; optional one-pole IIR time average. The spectrum trace and the waterfall share one `DbRange` (auto-range: slow one-pole follow of per-frame min/max with 5 dB headroom, SDR++-style, plus manual min/max) and one palette (the theme's JSON `waterfall` gradient; the spectrum uses its top stop, the waterfall the full gradient). Low-fi gating: the engine runs the FFT only when a display wants it (a shared `AtomicBool`), skipping it entirely when both are off. Frames reach the UI via a drop-oldest shared slot (`Mutex<Option<Frame>>`), taken once per draw. Takeaways: (a) the alternating-sign window is the clean way to center DC without an output fftshift; (b) our dB values are FFT-size-normalized so they won't match SDR++'s absolute scale: auto-ranging (not a fixed window) is what makes the trace fill the pane; (c) keep spectrum and waterfall on one dB range + one gradient so they stay visually consistent; (d) the ruler must label the tuned center at the middle column with auto-scaled Hz/kHz/MHz units, since a sub-MHz center rounds to "0" if you only place nice MHz ticks.
- 2026-10 (open polish items, not yet done): (1) the VFO marker column can drift a cell from the trace peak at some terminal widths because the trace peak-decimation columns and the marker's `freq_to_col` round independently: align the marker to the decimation column math when revisiting; (2) the spectrum dB window is not yet persisted; (3) the waterfall advances at UI-draw cadence (~10 Hz) not the full 20 fps FFT rate because the UI drains only the latest frame per draw: drain all pending frames if faster scroll is wanted; (4) mouse usability (click-to-focus/edit, draggable scrollbar, click-to-tune on the spectrum) is deferred as a batch.
- 2026-11: USB/LSB audio was unintelligible next to SDR++ (A/B recordings `wav/2026-11-04-*`, Rostov 8939 / Shannon 8957 Volmet). Root cause: the SSB/CW demods were never ported from SDR++, they were invented. (1) The "SSB detector" was `out = re -/+ im` per sample, which is not sideband-selective at all. (2) The channel low-pass was centered on the suppressed carrier, so it passed both sidebands. (3) An extra audio low-pass at bandwidth/2 cut SSB speech at 1.4 kHz. (4) CW multiplied the real audio by a cosine (adds sum/difference tones) and ignored the VFO tone setting. SDR++'s actual method is simple: the VFO reference for USB is the lower edge (REF_LOWER) and for LSB the upper edge, so the channel is extracted centered at carrier +/- bw/2 and the symmetric RxVFO filter selects one sideband; `dsp::demod::SSB` then shifts back by +/- bw/2 (`FrequencyXlator`) and takes `Re()`, followed by its AGC (setPoint 1.0, maxOut 10). No post-demod filter; audio spans 0..bw. CW is the same: shift the complex IQ by +tone, `Re()`, AGC. The full audit of every demod against SDR++ also fixed NFM/WFM deviation (= bandwidth/2, was hardcoded), added NFM's default-on audio low-pass (bw/2), WFM's 15 kHz/4 kHz audio low-pass and 50 us de-emphasis at 48 kHz, DSB default bandwidth 4600, and CW default tone 800 Hz (clamp 250..1250). Verified offline with `examples/ssb_chain_dump` (37 dB image rejection, 0.8 dB ripple 300..2700 Hz). Takeaways: (a) "port the reference" must cover EVERY block, including the ones that look trivial; a demod we wrote from memory was the worst bug in the app; (b) in SDR++ the sideband selection is done by the VFO reference + channel filter, not by the demodulator, so read the VFO/reference plumbing, not only `dsp/demod/*.h`; (c) test SSB with an opposite-sideband interferer and an upper-passband tone, not just "output is finite and non-zero" (the old SSB test proved nothing).
- 2026-11 (open): AM still uses the user-confirmed headroom AGC (`Agc::audio`, set point 0.3) instead of SDR++'s 1.0, for both the audio and carrier AGC; SSB/DSB/CW now use SDR++'s exact `Agc::sdrpp` (1.0) and clip like SDR++ does on loud peaks (the SDR++ reference recording clips ~1.5%; a steady 6-tone synthetic clips ~15%). Our IF rates are the channelizer's power-of-two rates (e.g. 31.25 kHz for SSB from 2 MHz) rather than SDR++'s exact 24 kHz; filters and AGC time constants are computed at the actual rate, so behavior matches, but an exact rational resample to the nominal IF is not done.
- 2026-11: After the SSB demod fix, the next A/B (`*-Fix01.wav`) still favored SDR++, but the PSD shape changed the diagnosis: ShellSDR's in-band spectrum was flat (+/-0.5 dB, noise-like) while SDR++ showed speech formants, and ShellSDR's out-of-band floor was uniformly ~8 dB higher all the way to 24 kHz. A demod/filter difference would change the shape at the passband edge; a uniform offset plus a flattened in-band means lower RF SNR. Root causes were in the Source plumbing, not DSP: gains/AGC were only sent at Start (never live), antenna and analog bandwidth were never sent at all, and the gain defaults were the range MIDPOINT (RSP RFGR 4.5, a fractional LNA state with heavy front-end reduction, which sets the noise figure on HF) that then got persisted. SDR++ defaults gains to the range minimum and applies every source control live. Takeaways: (a) read a PSD for its SHAPE: a uniform floor offset + flattened speech band points at SNR/gain, not filters; (b) verify each UI control actually reaches the hardware (trace UI field -> engine config/command -> device call), a value shown in the UI proves nothing; (c) defaults get persisted, so a bad default becomes the user's "setting": copy the reference tool's defaults; (d) RSP IFGR/RFGR are reductions (higher = less gain), label them so users don't invert them.
- 2026-11: With SDR++'s exact SSB AGC (setPoint 1.0, maxOut 10) the demod output routinely overshoots 1.0 (peaks ~2.2x on loud speech), which SDR++ handles by applying the volume to the unclamped float signal and letting only what still exceeds full scale clip at the sound card. We had a `clamp(-1, 1)` at the end of `VfoChain::process` and applied the volume afterwards in the cpal callback, so every peak was flattened at 1.0 and then scaled to the volume level: a rectangular waveform at ~0.45 (the user's volume), 14.4% of samples on the rail (A/B `*-Fix02.wav`; SDR++ had 1.1%), plus clipping distortion that showed up as the "+7 dB above the passband" floor. Fix: no clamp in the chain; limit only after volume in `engine::audio::output_sample`. Removing the clamp also raised the harness's measured image rejection from 37 to 66 dB (the clamp distortion had polluted that measurement). Takeaways: (a) the ORDER of gain stages and limiters matters as much as the stages: limit last, after every gain including volume; (b) a waveform pinned at a level other than 1.0 means a limiter upstream of a gain; (c) a histogram of |sample| (a spike in the top bin) is the fastest clip detector; (d) re-run old measurements after removing a distortion source, they may have been wrong.
- 2026-11: Live A/B recordings stopped being decisive: they are made one after the other, and two SDR++ takes of the same station differed by up to ~10 dB in pause-contrast and low-band metrics purely from HF propagation. The decisive method was an identical-input A/B: record a baseband IQ WAV in SDR++, play it in SDR++ and record the audio, and run the same file through our real chain offline (`examples/iq_wav_demod`). It immediately exposed a bug no synthetic test had caught: the channelizer's decimate-by-2 stages restarted their decimation phase at every block, so a block length that was not a multiple of the total decimation (SDR++ uses sr/200 = 1250 at 250 kHz; /8 gives 156.25) emitted an extra sample per block (+0.48% time base, a phase slip at the block rate). Our tests had always pushed one giant block. After carrying the phase, and matching the bandwidth SDR++ used, the outputs agreed at median 0.999 phase-invariant similarity. Takeaways: (a) every streaming block must be tested for block-boundary invariance (process whole vs in odd/uneven chunks, same samples, same count); (b) verify sample COUNT against `len * out_rate / in_rate`, a 0.5% excess is a bug; (c) compare SSB demods with a phase-invariant metric (analytic-signal correlation), since LO start phase differs and plain waveform correlation can be ~0 for identical-sounding audio; (d) match settings (here the SSB bandwidth: 2300 in SDR++ vs our 2800 default) before attributing differences to DSP; (e) keep analysis scripts in the repo (`tools/analysis/`), `/tmp` gets wiped.
- 2026-11: CW bandwidth was edited with the same global 500 Hz step and 500 Hz floor as every other mode, so CW (default 200 Hz, SDR++ range 50..500 Hz) could not be set below 500 Hz, and the first decrement from the default actually raised it to 500 Hz. Fix: bandwidth step and minimum are properties of the mode (`Mode::bandwidth_step`, `Mode::min_bandwidth`; CW 100/100 Hz, others 500/500 Hz), not one global constant. Takeaways: (a) an edit step and its clamp must fit the smallest value range they serve, so take them per mode from the reference tool's min/max bandwidth (`getMinBandwidth`/`getMaxBandwidth` in SDR++'s `demodulators/*.h`); (b) a clamp floor above a default is a bug signal: test stepping down from every mode's default; (c) narrower channels cost more filter taps (inverse to bandwidth), so a lower floor has a CPU price on the Pi.
- 2026-11: Bookmarks (Step 7) brought the first free-text input into a keyboard-accelerator TUI, which forced an explicit "text capture" mode: while a prompt, the editor form or the Find filter has the keyboard, printable keys are text (`translate_text_key`) and never accelerators, otherwise typing "q" into a name quits the app and "t" changes the theme. The first hands-on run then exposed two form-usability traps no unit test had asked about: (1) a fixed-width field (HHMM "0000") rejected typing because it was full; (2) after ENTER moved to the next field, typed digits were dropped because that field was not yet in edit mode. Fix: select-all-on-focus (typing replaces, arrows keep) and "type to edit" on a selected field, with the whole modal form in text-capture mode. Takeaways: (a) decide the text-vs-accelerator key model before the first text field; a modal form should own every key; (b) adopt standard form conventions (select all on focus, type to edit, Esc reverts the field then closes the form) rather than inventing; (c) drive the real binary in a pty (tmux `send-keys` + `capture-pane`) with a scratch `XDG_CONFIG_HOME` to catch interaction bugs that pure reducer tests encode as "expected".
- 2026-11: The bookmarks file is shared by all instances (user decision) while every other setting is per instance. Sharing needs (a) an atomic save (temp file + rename) so a reader never sees half a file, (b) saving immediately on change rather than on exit, and (c) noticing another instance's save (mtime polled once a second, reload keeping the selection by name). Without (b) and (c), "last closed wins" silently discards the other instance's bookmarks. Takeaway: for any state shared across processes, decide write timing and change detection at design time, not just the file location.
- 2026-11: Overlays that must line up with the spectrum (bookmark labels, VFO marker) share one geometry source (`spectrum::PLOT_LEFT_COLS`, `plot_columns`, `freq_to_col`) and one span (`AppState::display_span_hz`); a render test asserts the strip tick and the VFO marker land on the same column. Takeaway: never re-derive a sibling widget's column math, export it and lock alignment with a test.
- 2026-11: Source decimation and recording. (1) SDR++'s source decimator is not designed at runtime: it uses precomputed multi-stage plans with optimized taps (`decim/plans.h`, e.g. 64x = 8 * 4 * 2). We generated `dsp/decim_taps.rs` from those headers with a script rather than retyping 240 coefficients, and kept SDR++'s `DecimatingFIR` streaming rule (history + carried offset) with a block-boundary test from the start (lesson from the channelizer phase slip). (2) Everything that knew "the sample rate" had to be split into the device rate and the effective rate; `SourceModule::effective_sample_rate` is the one place, and the span, the engine and the baseband recording read it. (3) Recording: the DSP thread must never wait on the disk, so the writer is a thread fed by a bounded channel that drops (and counts) instead of blocking; the recorder is split into a DSP-side sink and a UI-side handle so stopping is "drop the sink, join the handle". (4) A classic RIFF file ends at 4 GiB, which a 2 MHz Int16 baseband reaches in ~9 minutes: split into parts, and decimation is the other half of the answer. Writing the ICMT after the data chunk lets it carry the real end time. (5) Never persist a "recording on" switch: a restart must not silently start writing files.
- 2026-11: CW tone limit raised to 3000 Hz (user request). Raising the clamp alone would have been a silent bug: the CW demod shifts the channel by the pitch at the IF rate (3906.25 Hz from 2 MHz, Nyquist 1953 Hz), so 3000 Hz would come out at ~906 Hz. Fix: the CW IF rate follows the pitch above SDR++'s 1250 Hz (`dsp::chain::cw_if_rate`), identical chain below it. Takeaway: a UI limit that mirrors a reference tool often encodes a DSP constraint; find the constraint before moving the limit, and test the new edge value end to end.
- 2026-11: Recording scheduler design was chosen by comparing options from three viewpoints (operator UX, architecture/cost, ops/YAGNI) before coding. Global bookmark-driven jobs beat per-VFO intervals (scattered, no source control) and event lists (edge-triggered, fragile after crashes and clock jumps). Implementation takeaways: (1) make a scheduler level-triggered ("which occurrence is open now?") and give occurrences an identity (start second), so restarts, missed ticks and NTP jumps need no special code; (2) drive the app's existing desired-state switches instead of the hardware, so the existing reconcilers do the work and the scheduler stays pure and testable; (3) distinguish user intent from failure by what the user action changes (Stop clears the recording switch, an engine failure does not); (4) inside one tick, account for your own effects (the planner first misread its own just-stopped recording as a manual one; a simulation test caught it); (5) independent constants in tests catch mistakes (a "Monday" timestamp that was a Sunday was caught by a weekday guard test).
- 2026-11: ShellSDR and SDR++ both hung at startup with no RSP attached. The cause was outside both apps: `SoapySDR::Device::enumerate("")` asks every installed module and waits for all, and the UHD module probes `localhost:5444` for embedded USRPs. IPv4 was refused at once, but `/etc/sysctl.d/99-disable-ipv6.conf` had disabled IPv6 on `lo`, so `::1` had no local address and was routed out of the WLAN, where the SYN was silently dropped and the blocking connect waited minutes. Found by timing `SoapySDRUtil --find=driver=X` per module, then `strace -f` on the slow one. Takeaways: (a) bisect a library-wide hang per plugin/driver before touching app code; (b) never call an all-drivers enumeration on the UI's startup path without a timeout (`enumerate_with_timeout`), and after a timeout do not touch the library again (it may still hold its factory lock); (c) "disable IPv6" must not include `lo`.
- 2026-11: Baseband file playback (spec 7.2). SDR++ had the useful rules: center from the file name's `[0-9]+Hz` (its recordings have no metadata), Int16 read as `/32768`, block size `rate/200`, and the center locked while a file is the source. Our own ICMT `center_freq` wins when present. Real-time pacing is a pure `Pacer` (frames due after t seconds) so it is testable; the DSP thread sleeps until the next 5 ms block is due and restarts the clock on a seek. UI rows that are text (file info, position) sit between fields, so the "field index = row" invariant the scroll and hit code relied on was replaced by `SourceModule::field_row`. Takeaway: when a module gains read-only rows, make the field-to-row mapping explicit instead of assuming one field per line.
- 2026-11: On some terminals the UI started with the shell's previous output (cargo, SoapySDR, ALSA lines) showing through, and on exit the whole UI stayed on screen and scrolled up: the alternate screen was not a fresh, separate buffer there. `EnterAlternateScreen`/`LeaveAlternateScreen` alone are not enough. Fix in `ui::run::run`: `Clear(All)` + `MoveTo(0,0)` right after entering and `terminal.clear()` to reset ratatui's diff buffers (full first repaint); a `restore_terminal()` that disables mouse capture, resets colors, clears the screen and homes the cursor *before* leaving the alternate screen, then shows the cursor and leaves raw mode, also called from a panic hook. Takeaway: never assume the alternate screen works; clear explicitly on both ends and make teardown best-effort and panic-safe.
- 2026-11: Release packages are built in Docker (`tools/dev build release arm64|x64`, `docker/Dockerfile.build`) on the oldest supported system per target (x64: `ubuntu:24.04`, arm64: `debian:trixie` with multiarch cross libraries), so the binary links against the oldest glibc/libSoapySDR/libasound it must run with; one Dockerfile parameterized by `BASE` and `ARCH`, compile only (no qemu, unlike the scheduler-station setup it was modeled on). Pitfalls hit: (a) Ubuntu 24.04's packaged `rustup` (1.26) fails at the end of `toolchain install` with "rustup is not installed at '/root/.cargo'" because it tries to self-update; use `--no-self-update` (the toolchain is selected with `RUSTUP_TOOLCHAIN`); (b) in a `set -e` bash script, a function called on the right of `||` runs with errexit disabled, so `inspect || build_image` silently ignored a failed `docker build`; use `if ! inspect; then build_image; fi`; (c) keep the container's `CARGO_TARGET_DIR` separate from the host `target/`, because build scripts compiled against the container's glibc must not be reused by the host (or the other way round). Takeaways: verify a "floor" claim by printing the binary's newest `GLIBC_` symbol version (`objdump -T`) after every build, and do not assume an `||` fallback in bash propagates errors.
- 2026-11: DSC (0.2.1) reused DSQrust's audio decoder by giving its demodulator a complex core: mixing by the mark and space tones already works on complex samples, so IQ centred on the DSC frequency is fed directly (mark +85 Hz, space -85 Hz) and audio becomes `(x, x)` into the same code. Proof: all 15 conformance audio vectors, mixed down to IQ, decode to the same symbols (`tests/dsc_iq_decode.rs`). Two traps: (a) the seed's raised-cosine filter divides by `sinc(2 i fc)` with `fc = 140 / rate`, which turns negative inside the passband below about 8 kHz, so a "cheap" 2-4 kHz channel decoded garbage; the channel stays at 8 kHz or more (`MIN_IQ_RATE`), which also sets the minimized-baseband floor; (b) the discriminator takes `trunc(ln(1 + |logic|))` of integer-scale levels, so the IQ (+-1.0 floats) must be normalized (a slow AGC to 8000 RMS) or weak signals round to zero. Takeaways: when porting a DSP algorithm to another rate or scale, look for constants that silently assume the original (rate-normalized filter terms, integer truncation), and prove the port against the original's own vectors.
- 2026-11: A Tune only job of another VFO type had its type restored on the next tick, because the restore ran whenever "no job is current" and only Record jobs are ever current. Found while specifying DSC's "Tune only keeps the type" rule. Takeaway: a restore-when-idle rule needs a test for every job kind that never becomes "current".
- 2026-11: FAX (0.2.2). The user's C++ fax decoder was used as a library through a small C API (`fax_c.h`, `libfax.so.1`, loaded with `dlopen`) instead of a Rust port: the decoder, its tests and its regression data stay in one place. Choices that paid off: (a) the live decoder keeps the demodulated signal (1 byte per sample at 12 kHz), not image lines, so straightening is only a different line length when drawing, with no decoding again; (b) C structs carry their size first, so the library and ShellSDR can grow independently; (c) the library starts no threads, the slant job copies its lines, so the caller decides where it runs; (d) a growing PNG stays valid by closing the zlib stream after every batch (empty final stored block, Adler-32, IEND) and rewriting the IHDR height and CRC, overwriting that tail with the next batch. Bugs found by measuring, not guessing: a false START inside a chart followed by chart lines with a frame line passed the old 10/90 phasing check (the fix checks that the lines look like phasing lines); the tone detector using only part of the line gave false START/STOP lines at 48 kHz (the whole line removed them all). Takeaway: when a decoder decides on a structure (a new picture), check that the expected content follows, not just that a trigger fired.
